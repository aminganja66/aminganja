01

The Problem — Trust Breaks Every Month

Indian residential societies manage hundreds of flats with no dedicated software. The result is the same argument, every month, between good people who simply lack a shared source of truth.

💬 Payment proofs lost in WhatsApp

Members send screenshots to a 300-message group chat. Admins scroll for 45 minutes verifying who paid. One missing screenshot becomes a month-long dispute.

⚔️ Monthly disputes between neighbours

"Mera toh paid hai!" The admin can't verify. The member can't prove it. Trust between committee and residents erodes over time — not from bad intent but from missing information.

📊 Zero expense transparency

Society funds are spent with no digital trail. Members have no way to see where their maintenance money goes. Suspicion builds. Meetings get heated.

🕐 45 minutes of manual work per month

Society admin cross-references WhatsApp, Excel, and bank statements every month by hand. No automation. No audit trail. Completely dependent on one person's memory.

💡

Core insight: The problem is not bad people — it is a missing system. When everyone can see the same truth, arguments become structurally impossible. The solution needed to be built around transparency as a first principle, not as a feature.

02

The Solution — One Source of Truth for Everyone

My Society Ledger digitises every step of the maintenance cycle. From admin generating dues to member uploading proof to admin approving — all in one app, with full visibility for every party.

STEP 01

Admin configures society once

Set maintenance amounts for owners and tenants separately. Configure due dates, penalty amounts, and grace periods. System generates 12 months of dues for all flats automatically — zero manual work every month.

STEP 02

Members get a permanent digital record

Members see their dues, due dates, and history in one place. They pay via UPI or bank as usual — then upload the screenshot in 30 seconds. Single month or multiple months in one submission. Partial payments supported for large fees.

STEP 03

Admin approves with one tap

Admin views the proof image, approves or rejects with a note. Push notification sent to member instantly. Approved records are permanent — tamper-proof, searchable, always available. "Did I pay?" is answered in seconds.

STEP 04

Both sides always see the same truth

Admin sees every flat's 12-month payment status on one screen. Members see their full history. Society expenses are visible to all members. When everyone sees the same data, disputes cannot exist.

03

The Process — How We Built It

A structured, step-by-step development process. Every decision reviewed before implementation. No code written without a clear plan.

PHASE 01

Problem definition and MVP scoping

Started with the real problem — not a feature list. Mapped every pain point in the existing WhatsApp + Excel workflow. Cut the initial feature list from 10 to 3 core flows: auth, flat management, and maintenance cycle. Everything else was deferred. Ship something focused rather than build everything and ship nothing.

PHASE 02

Schema design — entities vs events

Designed the database to answer two questions: who exists, and what happened. Started with 4 tables. Discovered quickly that there was no place to store events — payment submissions, approvals, expenses. Rebuilt to 12 tables. The key insight: dues and payments are different tables because they have different lifecycles, different creators, and different data.

PHASE 03

RPC-first backend — all logic in PostgreSQL

Decided early that Flutter would contain zero business logic. Every operation — creating a flat, submitting proof, approving a payment — is a single Supabase RPC. RPCs run as SECURITY DEFINER, handle validation, execute atomically, and return exactly what Flutter needs. 44 RPCs written and tested before the UI was touched.

PHASE 04

Clean Architecture + BLoC — feature first

Feature-first folder structure with strict layer separation. Every feature has data, domain, and presentation layers. BLoC split into three files — bloc, event, state. Repository returns Either<Failure, T> via dartz. No exceptions reach the UI. Each feature is independently testable and replaceable.

PHASE 05

Iterative feature expansion — with review at every step

New requirements arrived mid-build — tenants, multi-society support, additional fees, multi-month payments, penalty config. Each addition was planned, reviewed, and then implemented. Multi-month payments is a good example: the initial plan suggested two new tables. After review, a single column on the existing table solved it cleanly. Review before build saved the schema multiple times.

PHASE 06

Push notifications + production readiness

OneSignal integrated with multi-device support — player_ids stored as a TEXT array per user, appended on login and removed on logout. RPCs return notification payload directly so Flutter just reads and sends. Finally, a dev-to-prod migration plan created using Supabase CLI schema dump — ensuring production matches development exactly.

04

AI-Augmented Development with Claude

This project was built using AI-augmented development — not vibe coding. Every AI suggestion was reviewed, challenged, and understood before implementation.

🤖

AI-augmented development is not "AI writes my code." It is using AI as a product manager, architect, and senior reviewer that pressure-tests your decisions before you commit to them. The developer still owns every decision — AI accelerates the thinking, not the typing.

Claude as Product Manager

Planning features before touching code

Every feature was described in plain English first. Claude returned edge cases, failure scenarios, and user flow issues before a single line was written. The multi-society problem — where the same user could be admin in one society and member in another — was caught in planning, not in production.

INPUT
"I want to add role to the users table so each user has one role globally"
CHALLENGE RECEIVED
"What if the same user is admin in Society A and member in Society B?"
RESULT
Role moved to user_flats — scoped per flat, per society. Multi-society unlocked.
Claude as Backend Engineer

44 RPCs written, reviewed, and deployed

Supabase RPCs were written with Claude Code using the MCP server — which reads the live database schema before generating any function. Each RPC was reviewed line by line before deployment. Not blindly accepted — every guard, every JOIN, every return value was understood before it touched production.

WORKFLOW PER RPC

02 Claude reads live schema via MCP
03 Review SQL before approving

Knowing When to Push Back

AI suggestions are starting points, not final answers

When implementing multi-month maintenance payments, Claude suggested creating two new tables. After reviewing the plan, it was clear that a single group_id column on the existing payments table solved the problem completely. The ability to review and challenge AI output is what separates AI-augmented development from blindly generated code.

INITIAL SUGGESTION
Create 2 new tables for multi-month payment grouping — more complex schema
REVIEWED + CHALLENGED
"Can we just add group_id to the existing payments table?"
FINAL SOLUTION
1 tiny table + 1 column. Same result. Far simpler schema. ✓
Claude as Flutter Engineer

Clean Architecture prompts with strict rules

Claude Code was used inside the IDE with strict rules embedded in every prompt — max 200 lines per file, one class per file, BLoC split into three files, all colors from AppColors, all RPC names from RpcConstants. AI accelerated feature development while the architecture rules enforced quality. Speed without compromise.

Tech Stack

Every tool chosen for a specific reason — not because it was popular.

Mobile Flutter Single codebase for Android + iOS. Strong typing. Excellent widget system.
State Management flutter_bloc Predictable state. Testable. Clear separation of UI and business logic.
Backend + DB Supabase PostgreSQL with auth, storage, and realtime. Managed. Production-ready.
Database PostgreSQL 17 44 SECURITY DEFINER RPCs. All logic server-side. Zero raw queries in Flutter.
Auth Phone OTP + Twilio No passwords. Members login with the phone number admin registered.
DI GetIt + Injectable Compile-time dependency injection. No service locator anti-patterns.
Navigation GoRouter Role-based route guards. Deep linking. Declarative navigation.
FP dartz Either<Failure, T> for all repository methods. No uncaught exceptions.
Codegen Freezed + JsonSerializable Immutable models. copyWith. Exhaustive pattern matching on states.
Push OneSignal Free tier. REST API for targeted delivery. Multi-device array support.

Plan first. Build second. Always.

Every feature was described and reviewed before a line of code was written. The multi-month payment feature is the clearest example — initial plan suggested two new tables, review revealed one column was enough. The review step is where most of the value was created.

🏗️

Early architecture decisions compound over time

Putting role in user_flats instead of users was a week-one decision that made multi-society support straightforward in month four. Good architecture choices pay compound interest.

🤖

AI-augmented development is a skill, not a shortcut

Using Claude AI throughout this build was not about generating code faster. It was about having a collaborator that challenged assumptions, caught edge cases, and pressure-tested decisions before they became technical debt. The skill is knowing when to accept, when to push back, and when to go a completely different direction.

🔒

Security built in is easier than security retrofitted

RLS on all 12 tables and SECURITY DEFINER on all 44 RPCs was decided on day one. Database-level security means no Flutter bug can accidentally expose another society's data. This would have been extremely painful to add after the fact.

📦

Real requirements never arrive all at once

Tenants, multi-society support, additional fees with partial payments, penalty config, multi-device push — none of these were in the original plan. The architecture absorbed every addition cleanly because it was built for extension, not for the minimum.
